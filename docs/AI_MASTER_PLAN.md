## 0. System Philosophy

DiskTracker is a zero-config Windows file-system observation daemon written in Rust.
The user-facing surface is intentionally tiny — three commands. Everything else
(scanning, watching, reducing, storing) happens invisibly inside a background daemon.

```
disktracker init       # one-time: create storage, register/start the daemon, kick off indexing
disktracker status     # ask the running daemon how it's doing
disktracker doctor     # diagnostics: permissions, journal, DB integrity
disktracker uninstall  # stop the daemon and remove everything init created
```

No `scan` or `watch` command is ever exposed to the user. `init` triggers both internally.

**Scope lock:** this document covers Epoch 1 only — reliable, real-time mirroring of the
Windows file system into a local SQLite database. Do **not** implement search, snapshots,
history diffing, or AI/insights (see §9). Those are Epoch 2 and depend on data this epoch
produces.

## 1. Architecture Invariants (do not violate)

1. **Dependency direction is one-way:** `apps → api → core services → infrastructure → platform`.
   Nothing above `platform/windows` may reference a Win32 type directly. Nothing in
   `storage`/`pipeline` may reference the CLI.
2. **The CLI never touches SQLite directly.** It only speaks JSON-RPC 2.0 over a local
   named pipe (`\\.\pipe\disktracker`) to the daemon.
3. **Event sourcing, not direct mutation:**
   `USN Journal → RawEvent → mutation_log (append-only) → Reducer → facts (UPSERT, current state)`.
   `facts` always holds exactly one row per file identity (`file_id`), never per path.
4. **Identity over path.** A file/folder is identified by `file_id` (NTFS file reference
   number), not by its path string. Renames change the name/parent, not the identity.
5. **Path is derived, not stored as a flat string.** See §4.
6. **Startup ordering is strict:** the USN watcher starts *before* the baseline scan so no
   live event is ever missed, but the Drain Engine is blocked from touching `facts` until
   the baseline scan finishes and a reconciliation pass runs. See §5.
7. **`uninstall` must fully reverse `init`.** Nothing `init` creates is allowed to be
   forgotten on uninstall — service registration, DB files, config, and pipe artifacts.
   See §7.1.
8. **Progress observability must be free.** Live status/progress data (daemon PID, DB path,
   scan/watcher/drain counters) is maintained via in-memory counters updated directly by the
   threads doing the work, never via SQL queries or extra locking that could contend with
   the Drain Engine's writes or the API layer's reads. See §11.

## 2. Target Environment & Build Pipeline

Development happens in WSL; the binary is cross-compiled for Windows GNU and must be
**executed and manually verified on a native Windows host** (Win32 calls like the USN
Journal don't function correctly from inside WSL).

```bash
rustup target add x86_64-pc-windows-gnu
sudo apt-get install mingw-w64
cargo build --target x86_64-pc-windows-gnu
# binary: target/x86_64-pc-windows-gnu/debug/disktracker.exe
```

Run every test from a **native Windows PowerShell**, not WSL. USN Journal access requires
an elevated (Administrator) PowerShell session.

## 3. Cargo Workspace Layout

```
apps/

crates/
  core/                # domain types: RawEvent, Mutation, Fact — no OS, no SQL
  config/
  api/                 # JSON-RPC 2.0 server over named pipe
  platform/
    traits/            # generic PAL interface
    windows/           # USN Journal, MFT, Win32 — the ONLY crate allowed to touch Win32
  scanner/             # one-shot baseline crawl
  pipeline/            # normalizer, dedup, reducer
  storage/             # SQLite schemas + repositories (WAL mode — see §7)
  telemetry/
  common/
```

## 4. Core Domain Schemas (fixed — do not redesign mid-implementation)

```rust
// crates/core — produced identically by Scanner and Watcher
pub struct RawEvent {
    pub volume: String,
    pub file_id: u64,
    pub parent_file_id: u64,
    pub usn: Option<u64>,       // Some from Watcher, None from Scanner
    pub name: String,           // file/dir name only, not a path
    pub reason: RawEventReason, // Created, Modified, RenamedOld, RenamedNew, Deleted
    pub attributes: u32,
    pub is_directory: bool,
    pub size: u64,
    pub timestamp: chrono::DateTime<chrono::Utc>,
}

// crates/pipeline — after Normalizer/Dedup/RenameMatcher
pub struct Mutation {
    pub mutation_id: String,    // ULID
    pub file_id: u64,
    pub parent_file_id: u64,
    pub name: String,
    pub kind: MutationKind,     // Created | Modified | Renamed | Deleted
    pub size_delta: i64,
    pub at: chrono::DateTime<chrono::Utc>,
    pub source: MutationSource, // Watcher | Scanner | Recovery
}

// crates/storage — the current-state view, ONE ROW PER file_id
pub struct Fact {
    pub file_id: u64,           // PRIMARY KEY
    pub parent_file_id: u64,    // FOREIGN KEY -> facts.file_id (nullable for volume root)
    pub name: String,           // just this segment, e.g. "invoice.pdf"
    pub is_directory: bool,
    pub size: u64,
    pub created_at: chrono::DateTime<chrono::Utc>,
    pub modified_at: chrono::DateTime<chrono::Utc>,
}
```

### Why path is NOT a stored field

If `Fact.path` were a flat string, renaming a folder with 100,000 descendants would require
rewriting 100,000 rows even though the USN Journal only emits **one** rename event (for the
folder itself — children are untouched because their `parent_file_id` didn't change).

Instead: `path` is **computed on read** by walking `parent_file_id` up to the volume root
and joining `name` segments (cache this walk in memory — an in-memory
`file_id -> (parent_file_id, name)` map rebuilt from `facts` at daemon startup is enough,
it's just two integers and a string per file). A rename becomes a single-row UPDATE of
`name`/`parent_file_id` on the renamed folder's own row. Full paths are never persisted.

## 5. Startup Sequence (must be exact)

```
1. Record current USN cursor for the volume (usn_start).
2. Spawn Thread B (Watcher) immediately:
     - reads journal from usn_start onward
     - appends every RawEvent -> mutation_log (append-only, no facts writes)
3. Spawn Thread A (Scanner) immediately, in parallel:
     - crawls the volume via MFT/directory enumeration
     - bulk-UPSERTs discovered files into facts
     - does NOT read mutation_log, does NOT block on Thread B
     - on completion: signals done, terminates
4. Drain Engine stays idle/blocked while Thread A is alive.
   Any API/status call during this window reports state = "baseline_scanning".
5. When Thread A signals done:
     - Drain Engine replays mutation_log from usn_start (the cursor recorded in
       step 1 — not from record 1, so only the overlap window is replayed)
     - groups by file_id, reduces to net state, UPSERTs into facts
6. Drain Engine transitions to live mode: every future Watcher event is
   reduced and UPSERTed continuously.
```

Safe because `facts` convergence via UPSERT-by-`file_id` is order-tolerant for the overlap
window — scanner snapshot and watcher mutations resolve to the same final state regardless
of application order, as long as timestamps are compared.

## 6. USN Journal Implementation Notes

- Renames arrive as **two separate journal records** — `USN_REASON_RENAME_OLD_NAME` then
  `USN_REASON_RENAME_NEW_NAME` — matched by adjacent USN sequence number and shared
  `file_id`. Never treat rename as a single record.
- The journal must exist on the target volume (`fsutil usn createjournal ...`). `doctor`
  must check for this and report a clear, actionable error — don't silently create one.
- Reading the journal requires an elevated process (Windows Service running as
  `LocalSystem` satisfies this automatically; interactive dev/testing needs
  "Run as Administrator").
- Directory renames only produce one event, for the directory's own `file_id` — never
  enumerate/update children; this is handled for free by path derivation (§4).

## 7. Storage Notes

- Use **WAL mode** (`PRAGMA journal_mode=WAL`) from the first `init` — Drain Engine writes
  and API-layer reads run concurrently; default rollback-journal mode will produce
  `database is locked` errors under load.
- `mutation_log` schema:
  `sequence INTEGER PRIMARY KEY AUTOINCREMENT, file_id, parent_file_id, name, kind, size_delta, at, source`
- `init` must be idempotent: re-running it against an existing DB/service should detect the
  existing installation and report status rather than recreating schemas or re-registering
  the service.

## 7.1 Uninstall Command

`disktracker uninstall` must reverse everything `init` did, leaving the machine as if
DiskTracker had never been run. It is destructive and must be treated that way.

**Sequence:**
```
1. Check if the daemon is running (attempt to connect to the named pipe).
   - If running: send a graceful shutdown request over the pipe (not a process kill),
     and wait for it to release its SQLite file handles before continuing.
   - If not running (pipe unreachable): proceed — this is not an error, just log it.
2. Unregister the Windows Service (if one was registered by init). Use the same
   mechanism init used to register it, in reverse (e.g. sc.exe delete).
3. Delete the SQLite files: disktracker.db, disktracker.db-wal, disktracker.db-shm.
4. Delete the config directory/files created under AppData.
5. Print a summary of exactly what was removed (service, DB files, config path) so the
   user has a record of what happened.
```

**Safety requirements:**
- `uninstall` must prompt for explicit confirmation before deleting anything
  (e.g. require the user to type `yes`, or pass `--force` to skip the prompt
  non-interactively). This is destructive and irreversible — there is no snapshot or
  recycle-bin step for the DB itself.
- If the daemon fails to shut down gracefully within a reasonable timeout, `uninstall`
  must say so explicitly rather than force-killing it and deleting files out from under
  an active writer — a mid-write SQLite file deletion is exactly the kind of corruption
  this architecture is otherwise careful to avoid.
- `uninstall` must be safe to run twice in a row — if files/service are already gone,
  report "already uninstalled" per item rather than erroring.
- `uninstall` does **not** touch the actual tracked files on the user's disk — it only
  removes DiskTracker's own state (DB, service registration, config). Never delete
  anything outside DiskTracker's own AppData/service footprint.

## 8. Loop-by-Loop Build Plan

Each loop ends with a **manual verification step on native Windows**. Do not begin the next
loop until that step passes and `PROGRESS.md` is updated.

### Loop 1 — CLI & Named Pipe IPC
Build `apps/cli`, `crates/api`, `crates/core`. Wire JSON-RPC 2.0 over
`\\.\pipe\disktracker`. `init` starts a foreground daemon (dev mode); `status` sends a
request and gets back a hardcoded dummy response.
**Verify:** Window 1: `.\disktracker.exe init`. Window 2: `.\disktracker.exe status` →
prints dummy JSON.

> **Addendum (2026-07-08, see §11):** the dummy `status` response built in this loop should
> already use the full `ProgressSnapshot` shape from §11.3 (with zeroed/placeholder field
> values), so Loop 5 only has to wire in real data rather than reshape the response later.
> `init`'s polling/attach behavior from §11.4 is also part of this loop's CLI work, even
> though every field it displays is still fake until Loop 5.

### Loop 2 — Storage Schemas
Implement `crates/storage`. On `init`, create `disktracker.db` (WAL mode) under the local
AppData path with `facts` and `mutation_log` per §4/§7 if it doesn't already exist.
**Verify:** delete any existing DB, run `init`, kill it, open the `.db` file, confirm both
tables and WAL mode are present.

### Loop 3 — Dual-Threaded Core (Scanner + Watcher)
Implement `platform/windows` and `scanner` per §5 steps 1–3. Both threads log raw activity
to console; neither writes reduced state yet.
**Verify:** run `init` (elevated). Console shows the scanner crawling directories. While it
runs, create/rename/delete a file in Explorer — console shows corresponding raw USN log
lines concurrently.

### Loop 4 — Pipeline, Reducer, Deferred Drain
Implement `crates/pipeline` and the Drain Engine exactly per §5 steps 4–6, including rename
pairing per §6.
**Verify:** run `init` against a folder with thousands of files. While the scan is still
running, rapidly edit/rename a test file several times. Wait for scan completion, stop the
daemon, inspect the DB: `mutation_log` shows the full history; `facts` has exactly one row
for that file with the correct final name/parent/size. Then test §4 directly: rename a
folder with many files inside it and confirm only one `facts` row changes.

### Loop 5 — Diagnostics
Wire real data into `status` (baseline_scanning vs live, row counts, mutation_log size,
uptime) and implement `doctor` (pipe reachable, journal exists and enabled, DB integrity,
elevation check, AppData write permission).
**Verify:** `status` during scan reports `baseline_scanning`; after scan, reports `live`
with real counts. `doctor` reports pass/fail per check, including a deliberately-broken case
(e.g. run unelevated) to confirm a clear error rather than a crash.

> **Addendum (2026-07-08, see §11):** "wire real data into `status`" now means populating
> every field of the §11.2 `ProgressSnapshot` (PID, DB path, scanner counters/current path,
> watcher event count, drain replay progress) — not just the phase and row counts. Verify
> `init`'s live-updating status line (§11.4) alongside the plain `status` one-shot printout
> (§11.5); both must show the same underlying numbers at any given moment.

### Loop 6 — Uninstall
Implement `uninstall` per §7.1: graceful daemon shutdown over the pipe, service
unregistration, deletion of DB files and config, confirmation prompt / `--force` flag,
idempotent re-run behavior.

**Verify:** with the daemon running (service or foreground), run `disktracker uninstall`,
confirm the prompt, and check: the daemon process is gone, the Windows Service (if
registered) is no longer listed (`sc.exe query disktracker`), `disktracker.db` and its
`-wal`/`-shm` files are gone, and the AppData config directory is gone. Run
`disktracker uninstall` a second time immediately after — it must report "already
uninstalled" per item, not error or crash. Then run `disktracker status` — it should fail
cleanly (no daemon to connect to), not hang.

## 11. Live Progress Reporting (init & status)

### 11.1 Motivation

`init` previously started the daemon and returned with no feedback while the baseline scan
(which can take minutes on a large volume) ran in the background. Users need visible signs
of life: the daemon's PID, where the DB lives, what phase it's in, and live counters —
without violating any existing invariant (particularly #2 and #6).

### 11.2 Daemon-side: in-memory `ProgressSnapshot`

Add a `ProgressSnapshot` maintained in the daemon's shared in-process state (e.g. behind an
`RwLock`, with hot counters as atomics), updated directly by the Scanner, Watcher, and Drain
Engine threads as they work. This is read-only observability data — SQLite (`facts` /
`mutation_log`) remains the sole source of truth; losing this snapshot on daemon restart is
fine and expected.

```rust
pub struct ProgressSnapshot {
    pub daemon_pid: u32,
    pub db_path: std::path::PathBuf,
    pub started_at: chrono::DateTime<chrono::Utc>,
    pub state: DaemonState,          // Starting | BaselineScanning | Reconciling | Live
    pub scanner: ScannerProgress,
    pub watcher: WatcherProgress,
    pub drain: DrainProgress,
}

pub struct ScannerProgress {
    pub dirs_scanned: u64,
    pub files_scanned: u64,
    pub current_path: Option<String>, // updated at directory granularity, not per-file
}

pub struct WatcherProgress {
    pub usn_start: u64,
    pub events_buffered: u64,        // atomic counter, incremented alongside each
                                     // mutation_log append this session — never COUNT(*)
}

pub struct DrainProgress {
    pub replaying: bool,
    pub mutations_replayed: u64,
    pub mutations_total: Option<u64>, // known once the replay window is loaded, §5 step 5
}
```

Rules:
- No field here may require a SQL query on the hot path. Counters are incremented in-memory
  as each thread processes an item; `events_buffered` is a simple atomic bumped alongside
  each `mutation_log` append, not a `COUNT(*)` query.
- `current_path` updates once per directory entered, not once per file, to avoid lock
  contention on a hot Scanner loop.
- **No fabricated percentages.** Epoch 1 does not pre-walk the volume to learn a total file
  count, so progress is shown as running counts and the current path — never as "42%
  complete." Do not add a pre-count pass to manufacture a percentage; that's a separate,
  heavier feature and out of scope for this epoch (see §9).

### 11.3 API: extend `status`, don't add a new command

Extend the existing JSON-RPC `status` response to return the full `ProgressSnapshot`. This
is additive — `status` already exists (§0) and its shape only gains fields, it does not
change meaning or break existing callers.

### 11.4 CLI: `init` attaches and streams

`init`'s foreground behavior changes as follows (a Windows Service has no attached terminal,
so this only applies to interactive/dev-mode `init`):

1. `init` starts/registers the daemon exactly as before (§5) — no change to startup
   ordering or thread spawning.
2. Once the daemon is reachable over the pipe, `init` enters a polling loop: call `status`
   on a short interval (e.g. every 250ms) and render a single, in-place-refreshing status
   line — PID, DB path, phase, live counters, current path.
3. When `state` transitions to `Live`, print a final confirmation line and return control to
   the shell. The daemon keeps running in the background exactly as it already would —
   `init` returning does not stop it.
4. If the user interrupts (Ctrl+C) `init` during this polling loop, the daemon is
   **unaffected** — the loop only ever reads `status`, it never issues a shutdown. This is
   called out explicitly so a future agent doesn't wire Ctrl+C to a pipe shutdown call by
   mistake (that would contradict §7.1, which reserves graceful shutdown for `uninstall`).
5. This polling loop must not violate invariant #2 — it is repeated calls to the existing
   `status` RPC only, never direct SQLite access from the CLI.

### 11.5 `status` command also benefits

Running `disktracker status` by hand (§0) prints the same richer snapshot as a single
one-shot printout — not the polling/refresh behavior, which is `init`-only — giving a manual
way to check progress mid-scan without needing to have run `init` in the foreground.
